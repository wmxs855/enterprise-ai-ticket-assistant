# 技术设计与代码导读

## 阅读目标

阅读本文不需要记住每一行代码，重点是三件事：知道请求经过哪些文件；知道每层为什么存在；能从关键函数入口理解业务如何执行。

## 一条最重要的主线

```text
用户点击网页按钮
  → web/app.js 发送请求
  → src/api.py 校验输入并选择端点
  → src/workflow.py 判断意图并组织步骤
  → 知识检索、分类模型或数据库完成具体工作
  → 结果沿原路径返回网页
```

理解系统时应先沿业务主线追踪请求，再分析每个工具在主线中解决了什么问题。

## 第一层：网页交互

### 相关文件

- `web/index.html`：定义标题、表单、按钮和结果区域。
- `web/styles.css`：控制颜色、间距、双栏和手机单栏布局。
- `web/app.js`：读取输入、发送请求并显示结果。

### 从哪里开始读

先看 `web/app.js` 中四个 `addEventListener`。这个函数表示“当某个事件发生时执行指定程序”。四个事件分别对应知识问答、创建工单、查询工单和关闭工单。

所有网络请求都经过 `request` 函数。集中处理的原因是：请求头、错误读取和状态判断只写一次，其他功能不必重复。

### 设计说明

“前端只负责收集输入和展示结果，不决定权限是否通过。即使调用者绕过网页，后端仍会重新校验。”

## 第二层：后端接口

### 相关文件

- `src/api.py`

### 请求结构

`AssistantMessageRequest`、`CreateTicketRequest` 和 `CloseTicketRequest` 是请求结构。它们规定字段类型、最小长度、最大长度和允许的角色。

`StrictTextModel.strip_text` 会删除文字首尾空格。原因是只包含空格的描述看起来有长度，实际上没有业务内容。

### 创建应用

`create_app` 创建 FastAPI 应用，同时创建数据库仓库和工作流对象。测试可以传入独立数据库路径，因此不会污染演示数据。这种“从外部传入可替换组件”的思路也体现了依赖注入。

### 装饰器

`@application.post("/v1/tickets")` 是装饰器。它告诉 FastAPI：收到这个路径的提交请求时，调用紧随其后的函数。

端点函数只做三类事：校验请求、调用业务层、把业务错误转换成合适的网络状态码。它不应该重新实现分类和数据库规则。

## 第三层：工作流

### 相关文件

- `src/workflow.py`

### 最重要入口

`WorkflowEngine.handle` 是整个项目最值得熟悉的函数。它接收用户消息、用户编号、用户角色和是否批准，然后执行以下分支：

1. `knowledge_question`：调用知识助手。
2. `create_ticket`：预测类别、判断优先级并创建工单。
3. `query_ticket`：提取编号并按权限查询。
4. `close_ticket`：先检查人工确认，再按权限关闭。

`determine_intent` 当前使用明确关键词，而不是大语言模型。优点是便宜、快速、可预测、容易测试；缺点是语言表达变化较大时识别能力有限。

### 为什么这叫工作流而不是完全自主智能体

步骤和分支主要由程序提前规定，模型没有自由决定任意工具与执行顺序。因此更准确的说法是“带工具调用的确定性工作流”。这也是当前敏感业务更容易控制的选择。

## 第四层：知识检索与回答

### 相关文件

- `src/knowledge_base.py`
- `src/answer_generator.py`
- `knowledge/*.md`

### 初始化阶段

`KnowledgeBase.__init__` 完成三件事：

1. 使用 `split_document` 按标题和段落切分四份文档。
2. 使用字符级词频—逆文档频率学习文本特征。
3. 把十六个文档片段转换成数字向量并保存在内存中。

这些工作只在对象创建时完成，不能每次提问都重新学习，否则会浪费时间。

### 查询阶段

`KnowledgeBase.search` 把用户问题用同一个文本转换器变成向量，再计算它与全部文档向量的余弦相似度，最后按分数从高到低取前三项。

`KnowledgeBase.answer` 检查最高分是否达到 `0.20`。低于阈值时拒绝回答，高于阈值才返回原文与来源。

`KnowledgeAssistant.ask` 决定是否调用答案生成器。来源信息由程序附加，而不是让大语言模型自己编造。

### 当前边界

项目没有使用语义嵌入模型、向量数据库和重排序模型。十六个片段使用内存矩阵已经足够。数据扩大后，再加入关键词与语义混合召回、向量数据库和重排序更合理。

## 第五层：工单分类

### 相关文件

- `src/generate_training_data.py`
- `src/train_classifier.py`
- `src/workflow.py` 中的 `TicketCategoryPredictor`
- `models/ticket_category_model.joblib`

### 训练过程

`split_data` 把四分之三数据用于训练，四分之一留作测试，并使用 `stratify` 保持各类别比例一致。

`build_model` 创建机器学习流水线：先把字符转换成词频—逆文档频率数字特征，再交给逻辑回归分类。

`train_and_evaluate` 同时训练简单基准和正式模型。只有与基准比较，才能说明复杂模型是否真的产生价值。

训练完成后使用 `joblib.dump` 保存整个流水线。线上预测直接加载同一个文件，因此不会漏掉文本转换步骤。

### 当前边界

96.7% 来自三十条合成测试样本。数据较少、类别词明显、训练测试生成方式相同，因此只能验证流程，不能证明真实业务泛化能力。

## 第六层：数据库、安全与审计

### 相关文件

- `src/ticket_database.py`

### 仓库模式

`TicketRepository` 把数据库命令集中起来。工作流只表达“创建、查询、关闭”，不关心具体数据库语句。

### 连接作用域

`connection_scope` 使用上下文管理器保证连接最终关闭。此前测试曾发现：事务上下文会提交数据，却不会自动关闭 SQLite 连接，导致 Windows 无法删除测试数据库。增加 `finally: connection.close()` 后解决。

### 权限和审计

- 普通用户只能读取或关闭自己创建的工单。
- 管理员可以跨用户处理。
- 关闭必须传入明确批准。
- 创建和关闭与审计日志写入同一个事务，避免业务成功但日志丢失。
- 数据库使用参数化查询，输入只被当作数据。

## 两条请求的完整走向

### 问“一线城市住宿上限是多少”

1. 网页调用 `/v1/assistant/messages`。
2. 接口校验消息和用户编号。
3. 工作流判断为知识问题。
4. 知识助手检索十六个片段。
5. 差旅制度片段获得最高相关度并超过阈值。
6. 离线生成器返回证据原文。
7. 程序附加文件、章节和相关度。
8. 网页安全地显示答案与来源。

### 创建“员工无法登录内部系统”工单

1. 网页调用 `/v1/tickets`。
2. 接口拒绝空描述并清理首尾空格。
3. 工作流加载已训练流水线，预测为账号问题。
4. 优先级规则发现“无法登录”，判断为紧急。
5. 数据库事务写入工单和创建审计日志。
6. 新工单返回网页，编号自动填入查询框。

## 推荐阅读顺序

不要按文件夹字母顺序阅读。按真实执行顺序读：

1. `web/app.js`：请求从哪里发出。
2. `src/api.py`：请求如何进入后端。
3. `src/workflow.py`：如何选择分支。
4. `src/knowledge_base.py`：知识问题如何检索。
5. `src/answer_generator.py`：有证据后如何回答。
6. `src/ticket_database.py`：工单如何保存并检查权限。
7. `src/train_classifier.py`：分类模型如何离线产生。
8. `tests/`：每条承诺如何被验证。

## 设计要点总结

- 模块负责拆分职责，导入负责复用。
- 接口层、业务层和数据层不能互相重复实现规则。
- 类是设计说明，对象是使用某个配置创建出的实例。
- 装饰器把普通函数登记成网络端点。
- 工作流控制顺序，工具函数完成具体任务。
- 机器学习训练发生在离线阶段，预测阶段只加载成品。
- 权限必须在后端和数据库访问路径上强制执行。
- 测试应覆盖成功、边界、异常和安全场景。
