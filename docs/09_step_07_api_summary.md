# 第 7 步第一部分总结：后端服务与接口评测

## 本步目标

把第 6 步已经验证过的知识问答和工单工作流封装成后端服务，让浏览器、演示页面或其他程序能够通过统一网络请求使用它。

“应用程序编程接口”的英文全称是 Application Programming Interface，招聘描述中常写成 API。它不是人工智能算法，而是不同程序之间约定好的入口、输入和输出。

## 为什么需要这一层

前六步的功能只能通过 Python 命令直接调用。真实产品通常把用户界面和业务逻辑分开：用户界面发送请求，后端负责校验输入、检查权限、调用模型和数据库，再返回结构化结果。这样网页、手机应用和内部工具都能复用同一套业务规则。

## 本步完成的端点

| 操作 | 网络方法与路径 | 成功结果 |
| --- | --- | --- |
| 健康检查 | `GET /health` | 返回服务状态、版本与回答模式 |
| 完整工作流 | `POST /v1/assistant/messages` | 自动判断知识咨询或工单操作 |
| 创建工单 | `POST /v1/tickets` | 返回 201 和新工单 |
| 查询工单 | `GET /v1/tickets/{ticket_id}` | 检查权限后返回工单 |
| 关闭工单 | `POST /v1/tickets/{ticket_id}/close` | 经过确认和权限检查后关闭 |

`GET` 表示读取数据，`POST` 表示提交数据或触发操作。花括号中的 `ticket_id` 是具体工单编号。

## 输入与输出如何保护系统

- 问题描述和用户编号不能为空，并设定最大长度。
- 用户角色只能是普通用户或管理员，不能随意传入未知角色。
- 普通用户查询别人的工单时返回 403，表示禁止访问。
- 查询不存在的工单返回 404，表示没有找到。
- 关闭工单但尚未确认时返回 409，表示操作条件冲突。
- 空描述等不合格输入返回 422，业务逻辑不会执行。
- 响应也进行结构校验，避免后端悄悄返回缺失或错误字段。

## 测试中发现并修复的问题

第一次运行 35 项完整测试时，34 项成功，知识问答接口失败。原因是工作流实际返回的来源包含文件、章节和相关度，而接口响应结构多声明了一个正文必填字段。FastAPI 在返回前执行结构校验，因此主动报告错误。

修复方法不是伪造一个空字段，而是让公开响应结构与真实业务数据保持一致。修复后 35 项完整测试全部通过，说明新增服务层没有破坏旧功能。

## 评测结果

接口专项评测共 6 个场景，6 个全部通过：健康检查、知识来源、自动分类、越权拒绝、人工确认和空输入校验。详细状态码与本机单次耗时见 `reports/step07_api_evaluation.md`。

耗时只用于发现明显异常。进程内单次测试没有真实网络、并发用户和生产数据，不能据此宣称系统具备高并发能力。

## 当前安全边界

请求中的用户编号和角色由调用方直接提供，因此当前实现只是“权限规则演示”，不是真实身份认证。生产系统应由登录系统验证身份并签发不可伪造的凭证，后端再从凭证读取用户身份，而不是相信请求正文中的自报信息。

## 如何运行

在项目根目录执行：

```powershell
.\.venv\Scripts\python.exe -B -X utf8 -m uvicorn src.api:app --host 127.0.0.1 --port 8000
```

然后打开 `http://127.0.0.1:8000/docs`。这是自动生成的交互式文档，可以展开端点、填写请求并点击执行。`127.0.0.1` 表示只允许本机访问，适合学习和演示。

## 面试题与参考答案

### 问题一：为什么不在接口里重新实现工单逻辑？

参考答案：接口层只负责接收请求、校验数据和转换错误，核心业务继续复用已经测试过的工作流和数据库层。这样命令行和网页使用同一套规则，避免两份逻辑逐渐不一致。

### 问题二：为什么需要输入和响应两边都校验？

参考答案：输入校验能在业务执行前拒绝缺失、类型错误或过长数据；响应校验能检查实现是否遵守公开接口约定。本项目正是通过响应校验发现来源字段声明与真实结果不一致。

### 问题三：200、201、403、404、409 和 422 分别表示什么？

参考答案：200 表示成功；201 表示资源创建成功；403 表示已经理解请求但没有权限；404 表示目标不存在；409 表示当前状态与操作要求冲突；422 表示请求结构能够读取，但字段内容未通过校验。

### 问题四：为什么当前权限控制还不能用于生产？

参考答案：当前用户编号和角色来自请求本身，恶意调用者可以伪造管理员角色。生产环境必须先由可靠登录系统认证，再使用经过签名或服务端会话保存的身份信息。

### 问题五：健康检查有什么用？

参考答案：部署平台或监控系统可以定期调用轻量健康接口，判断服务进程能否响应。健康检查失败时可以报警或重启服务，但更完整的生产检查还应区分进程存活、数据库可用和业务就绪状态。

### 问题六：本机接口耗时可以证明系统性能好吗？

参考答案：不能。当前数字来自单机、进程内、少量数据和单次请求，只能发现明显退化。要评价生产性能，需要定义并发数、数据规模、延迟分位数、错误率、硬件环境和持续时间，并使用压力测试工具重复测量。
